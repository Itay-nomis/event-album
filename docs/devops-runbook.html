Stage 01

Run locally with Docker Compose

Do this now

The README marks this stage as done, but you haven't run it on this machine yet. The goal is to see all 5 services healthy, follow one photo through the whole system, and break things on purpose so you learn how the pieces depend on each other.

  1. Review the .env file

    A .env already exists and matches .env.example. All the containers read their settings from it. If you change the database password, change it in both POSTGRES_PASSWORD and DATABASE_URL.

    .env
    POSTGRES_USER=album
POSTGRES_PASSWORD=change-me
POSTGRES_DB=album
DATABASE_URL=postgresql://album:change-me@postgres:5432/album
REDIS_URL=redis://redis:6379/0
S3_ENDPOINT=http://storage:8333
S3_ACCESS_KEY=local
S3_SECRET_KEY=local
S3_BUCKET=photos

    Hostnames like postgres, redis and storage work because Compose puts every service on one network and gives each one a DNS name that matches its service name.

    GotchaPostgres sets the password only the first time it creates its data volume. If you change the password later, you have to recreate the volume with docker compose down -v, which deletes all the data.

  2. Validate the Compose file

    docker compose config

    This prints the final config with every ${VARIABLE} filled in. Get in the habit of running it before every up.

    CheckYou get no variable is not set warnings, and pg_isready -U album -d album appears in the Postgres healthcheck.

  3. Build the images and start the stack

    docker compose up --build -d
docker compose ps

    The first build downloads Python and installs the packages, which takes a few minutes. -d runs the stack in the background. Startup order comes from depends_on: the API and worker wait until Postgres and Redis report healthy.

    CheckIn docker compose ps, postgres, redis and api show (healthy), and worker and storage show Up. The API takes about 10 seconds to report healthy because its Dockerfile healthcheck polls /healthz.

  4. Call the health endpoint

    # In PowerShell, type curl.exe. Plain "curl" is an alias for Invoke-WebRequest.
curl.exe -i http://localhost:8000/healthz
    CheckYou get HTTP/1.1 200 OK. Later, CI and Kubernetes will call this same endpoint.

  5. Follow the logs in a second terminal

    cd C:\projects\event-album
docker compose logs -f api worker

    Keep this terminal open for the rest of the stage, so you can watch each request and job as it happens.

  6. Follow one photo through the system

    • Open http://localhost:8000 and create an event. Write down its code.
    • Open the venue screen (/e/<code>/show) in one tab and the upload page (/e/<code>) in another.
    • Upload a photo. To use your phone instead, open the app as http://<your-PC-LAN-IP>:8000 (find the IP with ipconfig) when you create the event, so the QR code points at an address your phone can reach.
    CheckThe API logs a POST …/photos request, the worker logs that it processed the job, and the photo appears on the venue screen without a page refresh.

  7. Look inside each service

    Each command below runs inside a running container with docker compose exec.

    # Postgres: events and photo info
docker compose exec postgres psql -U album -d album -c "select count(*) from photos;"

# Redis: jobs waiting in the queue (0 means the worker has caught up)
docker compose exec redis redis-cli llen jobs

# Redis: watch live "new photo" messages for one event (Ctrl+C to stop)
docker compose exec redis redis-cli subscribe event:<code>

# Storage: list the files in the S3 bucket
docker compose exec api python -c "import boto3,os; s=boto3.client('s3',endpoint_url=os.environ['S3_ENDPOINT'],aws_access_key_id='local',aws_secret_access_key='local'); [print(o['Key']) for o in s.list_objects_v2(Bucket='photos').get('Contents',[])]"
    CheckThe photo count matches the number of uploads, and the bucket holds both the original image and the processed one.

  8. Stop the worker on purpose and watch the queue

    docker compose stop worker
# now upload 3 photos from the browser
docker compose exec redis redis-cli llen jobs     # → 3
docker compose start worker
docker compose exec redis redis-cli llen jobs     # → 0, and the photos show up

    This is the main reason the app uses a queue. Uploads keep working while the worker is down, and nothing gets lost. Stage 5 builds on this: it adds workers automatically when the queue grows.

  9. Check that data survives a restart

    docker compose down       # removes the containers, keeps the volumes
docker compose up -d
docker volume ls          # event-album_pgdata, event-album_storagedata
    CheckYour event and its photos are still there. Containers are disposable, and the data lives in the named volumes.
    Carefuldocker compose down -v also deletes the volumes, which wipes the database and every photo.

  10. Pin the storage image version

    In docker-compose.yml, chrislusf/seaweedfs:latest means you can get a different version on every pull, so a build that works today can break tomorrow. Look up the current release tag on Docker Hub and use that tag in place of latest. Postgres and Redis are already pinned to major versions (16-alpine and 7-alpine).

    docker-compose.yml
      storage:
    image: chrislusf/seaweedfs:<exact-tag>

  11. Commit and push

    git add docker-compose.yml
git commit -m "Pin SeaweedFS image version"
git push

    .env is listed in .gitignore, so your secrets stay out of Git. Only .env.example gets committed.

Stage 02

CI with GitHub Actions

Next

On every push, GitHub lints the code, starts the whole stack, checks that /healthz answers, and on main publishes the api and worker images to GitHub Container Registry (GHCR).

  1. Work on a branch

    git switch -c ci-pipeline

  2. Run the linter locally first

    Ruff is a fast Python linter. Running it in a container means you don't need Python installed on Windows.

    docker run --rm -v "${PWD}:/io" -w /io ghcr.io/astral-sh/ruff:latest check api worker
    CheckYou see All checks passed!. The rules it checks are set in ruff.toml at the project root, so you get the same results on your PC and in CI. To fix simple problems automatically, add --fix.

  3. Add the workflow file

    .github/workflows/ci.yml
    name: ci
on:
  push:
    branches: [main]
  pull_request:

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install ruff
      - run: ruff check api worker

  smoke-test:
    needs: lint
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: cp .env.example .env
      - run: docker compose up --build -d --wait
      - run: curl --fail --retry 10 --retry-delay 3 --retry-all-errors http://localhost:8000/healthz
      - if: failure()
        run: docker compose logs
      - if: always()
        run: docker compose down -v

  push-images:
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    needs: smoke-test
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    strategy:
      matrix:
        service: [api, worker]
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: ./${{ matrix.service }}
          push: true
          tags: |
            ghcr.io/itay-nomis/event-album-${{ matrix.service }}:${{ github.sha }}
            ghcr.io/itay-nomis/event-album-${{ matrix.service }}:latest

    --wait makes Compose wait until every healthcheck passes. Each image is tagged with the commit SHA, so every image traces back to the exact commit that built it. Stage 4 deploys those SHA tags. Registry names must be lowercase, which is why the owner is written itay-nomis.

  4. Push the branch and open a pull request

    git add .github
git commit -m "Add CI: lint, smoke test, push images"
git push -u origin ci-pipeline
    CheckThe PR shows two green checks: lint and smoke-test. push-images is skipped because it only runs on main.

  5. Merge the PR and check the published images

    After you merge, open your GitHub profile → Packages. You should see event-album-api and event-album-worker.

    docker pull ghcr.io/itay-nomis/event-album-api:latest
    NoteNew packages are private by default. Before a cluster can pull them, either make them public in each package's settings, or give the cluster a pull secret (Stage 4).

  6. Protect the main branch

    In the repo, go to Settings → Branches → Add rule for main. Require pull requests and require the lint and smoke-test checks to pass. After that, broken code can't reach main.

Stage 03

Cloud infrastructure with Terraform

Later

Replace each local container with a managed cloud service. The app code stays the same because every connection is set through environment variables. That's why the app uses S3-compatible storage.

Steps (AWS shown as the example)

  • Set a budget alert first. In AWS Billing, create a monthly budget with an email alert, for example $20.
  • Create a separate IAM user or SSO role for Terraform. Don't use the root account.
  • Keep Terraform state in an S3 bucket with state locking, not on your laptop.
  • Map each local service to a managed one: postgres → RDS, redis → ElastiCache, storage → an S3 bucket (point S3_ENDPOINT at real S3 and use IAM credentials).
  • Put everything in a VPC. The database and Redis go in private subnets with no public access.
  • Store secrets in AWS Secrets Manager or SSM Parameter Store, not in .env.

Done when

  • terraform apply builds everything from nothing, and terraform destroy removes all of it, leaving no cost behind.

  1. Budget alert created

  2. Terraform state stored remotely

  3. Infrastructure built with apply and removed with destroy

Stage 04

Kubernetes and GitOps with ArgoCD

Later

Run the api and worker on Kubernetes. Git becomes the record of what's deployed, and ArgoCD keeps the cluster in sync with it.

Steps

  • Start on a local cluster with kind or k3d. It's free, quick to create, and quick to throw away.
  • Write manifests, or one Helm chart, in a deploy/ folder. You need a Deployment and Service for the api, a Deployment for the worker, an Ingress, and a Secret built from your env vars.
  • Give the api a readinessProbe and a livenessProbe on /healthz. It's the same endpoint the Dockerfile healthcheck uses.
  • Install ArgoCD and point an Application at deploy/.
  • Extend CI so that after it pushes images, it updates the image tag in deploy/ to the new commit SHA. ArgoCD notices the change and deploys it.

Done when

  • Merging a PR changes what runs in the cluster without any kubectl apply by hand, and reverting the commit rolls it back.

  1. App running on a local cluster

  2. ArgoCD keeping the cluster in sync with deploy/

  3. A merged PR deploys automatically

Stage 05

Scale for a 300-guest wedding

Later

Add workers when the jobs queue grows, then load-test the system to prove it holds up.

Steps

  • Install KEDA and create a ScaledObject with a Redis list trigger on jobs. For example: 1 worker per 20 queued jobs, between 1 and 10 workers.
  • Write a k6 script that uploads photos the way guests would: 300 guests sending bursts of photos during the first dance.
  • While the test runs, watch the queue length, the worker count and the upload latency.

Done when

  • The queue spikes, the worker count rises, the queue drains, and the workers scale back down, all without manual steps.

  1. Workers scale with queue length

  2. 300-guest load test passed

Stage 06

Observability

Later

Find out something is wrong before the bride does.

Steps

  • Install kube-prometheus-stack, which includes Prometheus, Grafana and Alertmanager.
  • Add a /metrics endpoint to the api (for example with prometheus-fastapi-instrumentator). Have the worker report how long each job takes and how many jobs fail.
  • Build one Grafana dashboard showing uploads per minute, queue length, processing time, and 5xx error rate.
  • Set up alerts for a queue longer than 100 for 5 minutes, an api error rate above 2%, and worker restarts.

  1. api and worker report metrics

  2. Grafana dashboard built

  3. Alert triggered once on purpose and seen

Troubleshooting

What you seeFix
failed to connect to the docker API … dockerDesktopLinuxEngineDocker Desktop isn't running. Start it and wait for Engine running.
Bind for 0.0.0.0:8000 failed: port is already allocatedAnother program is using port 8000. Find it with netstat -ano | findstr :8000, or change the mapping to "8080:8000".
api keeps restartingRun docker compose logs api. The usual cause is a missing variable in .env, which shows up as KeyError: 'DATABASE_URL'.
password authentication failed for user "album"You changed the password after the database volume was created. Either change it back, or run docker compose down -v to start fresh. This deletes all data.
Photo uploads, but never appears on the venue screenCheck whether the worker is running (docker compose ps), whether the queue is growing (redis-cli llen jobs), and read docker compose logs worker.
Phone can't open the QR linkCreate the event while browsing at your PC's LAN IP, not at localhost. Then allow port 8000 through Windows Firewall on private networks.
Code changes don't show upThe code is copied into the image at build time. Rebuild with docker compose up --build -d.
